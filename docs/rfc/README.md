# RFC

本目录存放 OpenDerisk Agent 框架的设计提案（Request For Comments），用于在动手编码前对齐架构方向。

## 写作原则

1. **机制 ≠ 框架**：RFC 提炼的是**机制**（最小可工作的代码模式），不是**框架**（一整套相互绑定的抽象）。判断标准：在现有 `core/` 上原地引入这个想法，所需新增代码量是否在该模块原代码量的 30% 以内；超出则说明抽象选错，需重新设计。
2. **每篇 RFC 一个想法**：粒度对齐"一个能独立合入并产生价值的 PR"，不堆叠依赖。
3. **方案脱离时间**：RFC 描述的是"应该怎么做"，不引用具体实现的临时代码模块。可以引用稳定的 core 模块（`SystemEventManager` / `RecoveryCoordinator` 等），不引用过渡期的实验代码。
4. **每篇 RFC 必须有「不做什么」**：明确反向、避免特性蔓延，是 RFC 最有价值的部分之一。
5. **粒度统一**：单篇 ≤ 300 行 markdown，超长意味着抽象未收敛、应拆分。

## 标准结构

每篇 RFC 建议按以下章节组织：

1. **背景与问题**：当前痛点、真实诉求来源。
2. **设计目标与原则**：本 RFC 想达成什么、坚持什么取舍。
3. **核心机制**：最小化的接口设计与数据模型。
4. **演进路径**：分步落地清单（每步独立可上线、独立可回滚）。
5. **不做什么**：明确反向、避免特性蔓延。
6. **验收标准**：可被测试或度量的 AC 列表。
7. **开放问题**：待与团队对齐的决策点。

## 状态字段

- `Draft` — 提案中，欢迎评论。
- `Accepted` — 已对齐，进入实施。
- `Implemented` — PR 已合入，相关代码已上线。
- `Superseded by RFC-NNN` — 被新 RFC 取代。
- `Rejected` — 经讨论决定不做，保留文档作为决策记录。

## 文件命名

- `RFC-NNN-kebab-case-title.md`，编号递增不复用。
- 即使被 `Rejected` / `Superseded`，文档也保留——决策记录本身有价值。
